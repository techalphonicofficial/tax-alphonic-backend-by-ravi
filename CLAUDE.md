# Tax Alphonic CMS backend

REST API for the Tax Alphonic CMS. It serves two clients:
- `../taxalphonic-cms-admin`: the admin panel. It uses JWT auth.
- The public website at `../taxalphonic-dynamic-frontend` (Next.js; the old `Desktop\tax\taxalphonic` copy is no longer used). It uses only the public GET routes and form submit.

## Stack and commands
- Express 5, Sequelize 6 + MySQL (`mysql2`), JWT, multer + sharp (uploads), nodemailer, winston, Swagger.
- `npm run dev` (nodemon `server.js`, port 5000). Not a git repo. `npm test` runs `tests/*.test.js` (node:test, no database: landing page subdomain rules and block validation).
- Migrations: `npx sequelize-cli db:migrate` (`.sequelizerc` points to `config/config.js`, `migrations/`, `seeders/`). `sequelize.sync` is commented out in `server.js`, so schema changes need a migration.
- The DB server (MariaDB on Linux, `lower_case_table_names=0`) is case-sensitive and every table name is lowercase. Give every model an explicit lowercase `tableName` (Sequelize otherwise uses e.g. `Industries`). Migrations use lowercase names too, and sequelize-cli keeps its history in `sequelizemeta` (`migrationStorageTableName` in `config/config.js`).
- Swagger UI is at `/api-docs` (spec in `docs/swagger.js`). Uploads are served from `/uploads`.
- `.env`: PORT, DB_* (DB_HOST, DB_PORT, DB_USER, DB_PASS, DB_NAME, optional DB_DIALECT), JWT_*, GEMINI_API_KEY. Never print or commit it. `config/config.js` builds the DB connection from DB_* for the app and sequelize-cli (same values in every NODE_ENV); there is no config.json.

## Layout
`routes/index.js` (mounted at `/api/v1`) → `routes/*Routes.js` → `controllers/` → `services/` (business logic, extend `BaseService`) → `repositories/` (extend `BaseRepository`) → `models/` (Sequelize, `models/index.js`).
- Responses always go through `utils/responseFormatter.js`: `{ success, message, data, errors, pagination? }`. Errors carry `errors: [{ field, message }]` (422 for validation).
- Auth: `middlewares/auth.js` provides `verifyToken` (`Authorization: Bearer`), `checkPermission(action, Module)`, `requirePermission(action, Module)` (both, spread: `...requirePermission(...)`) and `publicRead(Module, liveStatus)`. Public routes are declared BEFORE `router.use(verifyToken)` in each route file. Permissions are seeded by migrations (e.g. `*-seed-form-permissions.js`).
  - Every request reloads the user: a deactivated (`isActive` false) or deleted account is refused at once with **401** (the admin then logs out), even with an older token. Missing permission = 403. (`errorResponse` is `(res, message, errors, status)`.)
  - Only what the website (`../taxalphonic-dynamic-frontend`) or the login screen needs is public; everything else needs login + permission. Public now: auth login / forgot / reset (register needs `create Users`), `GET pages/slug/:slug` (a slug with a slash, e.g. Journey Stage pages `journey/idea`, arrives encoded as one segment), `GET pages/tools-list` (published pages with a `ToolCalculator` block → `{ slug, url, calculator, title, icon, tag, description, order }` from the ToolHero, ordered by order; `PageService.getTools`), `GET pages/journey-stages` (published pages with a `JourneyHero` block → `{ slug, url, number, title, shortLabel, icon, color, tag, roadmapText }` ordered by number; `PageService.getJourneyStages`), `services/slug/:slug`, `service-categories/:id`, `packages/:id`, `about-page`, `seo/lookup`, `seo-pages/lookup` + `by-service/:id`, `blogs/public/*`, `forms/public/*`, `POST inquiries`, `sitemap`, `settings/:group` only for organization / contact / address / social (other groups hold SMTP / payment secrets), and the module lists the homepage reads (`testimonials`, `faqs`, `team`, `banners`, `branches`, `partners`, `countries`, `portfolio-items`, `menus`) through `publicRead`: without a login that may read the module, every `status*` query key is replaced by the live status, so drafts never leave the API. A new website call to a protected route must be added here deliberately.
  - Route modules accept a list (any one is enough): the admin sidebar's module plus the specific one, e.g. `['CMS', 'FAQs']`, `['Portfolio', 'PortfolioItems']`, `['SEO', 'Locations']`, `['CRM', 'Inquiries']`, `['Blogs', 'BlogTags']`.
  - Uploads: auth runs before multer, so anonymous requests never write files.

## Key domains
- Services: `GET /services/slug/:slug` (public). It returns `sections[]` of `{ type: { componentKey }, config, data: { payload } }`.
  - Section types live in the `sectiontype` model. `ServiceService.saveServiceSections` auto-creates a type for any new `componentKey`, so new Page Builder blocks need no migration.
  - `config` is stored as given (a JSON string in responses). The website reads `placement`, `kicker` and `anchorId` from it. `ServiceController.getBySlug` (and `SeoPageController`, `PageService`, `BlogController`) run `services/SectionHydrator.js`, which embeds full `form` and `packages` objects into Form and Packages blocks. For services, pages and blogs, any block whose payload has a `formId` also gets its `form` (the homepage expert banner and newsletter use this). `FormService.hydrateServiceSections` also JSON-parses string payloads.
- Pages: `GET /pages/slug/:slug` (public, `status: "published"`). Blogs use the same hydrator for their `sections`.
- Landing pages (`/landing-pages`, full reference in `docs/LANDING_PAGES.md`): service landing pages on subdomains (`cbdt.taxalphonic.com`).
  - Tables `landing_pages` (service, title, unique subdomain `slug`, SEO, status draft|published|archived, `publishedVersionId`, `draftUpdatedAt` = unpublished changes, cleared on publish) and `landing_page_versions` (immutable snapshot per publish). Migrations `20261023000000-create-landing-pages.js`, `20261023000001-seed-landing-page-permissions.js`.
  - The draft is a `pages` row with slug `landing-page/<slug>` (always draft). `PageService` hides those rows from `GET /pages` and `pages/slug`, and refuses to publish / delete them or to reuse the prefix.
  - `LandingPageService`: create (template or the service's blocks), settings, save draft, validate, publish (one transaction: version N+1 + `publishedVersionId`), unpublish, archive / unarchive, versions, copy a version into the draft, delete an old version (never the live one; `publish` permission, audit-logged). `services/landing/subdomain.js` (label rules, reserved names, host parsing) and `landingValidation.js` (block checks) are unit-tested.
  - `LandingHeader` / `LandingFooter` blocks are the header / footer regions (one each).
  - Public: `GET /landing-pages/public/resolve?slug=|host=` returns only the published snapshot (hydrated), else 404.
  - Permissions module `LandingPages`: read, create, update, preview, publish, unpublish, archive. Env: `LANDING_BASE_DOMAINS` (default taxalphonic.com), `LANDING_RESERVED_SUBDOMAINS`.
  - Swagger now marks `requirePermission(...)` / `can(...)` routes as protected.
- Website blog (`BlogPublicController`, no auth, routes above `/blogs/:id`): `GET /blogs/public` (`?page&limit&category=<slug>&tag=<slug>&search`, cards without content: excerpt falls back to the first words, `readTime` to words/200, `date` = publishDate or createdAt), `GET /blogs/public/categories` (with live counts), `GET /blogs/public/:slug` (sections hydrated, FAQs, 3 `related`), `POST /blogs/public/:slug/view` (+1 viewCount, no audit). Likes / comments (`BlogEngagementController`, migration `20261019000000-blog-likes-and-comments.js`): `GET /blogs/public/:slug/engagement?visitorId=`, `POST .../like {visitorId, liked}` (sets, not toggles; `blog_likes` unique per blog+visitor, `blogs.likeCount` recounted), `GET .../comments?cursor=&limit=&visitorId=` (approved only, newest first, base64url cursor `createdAt|id`), `POST .../comments {name, email?, body, visitorId, _hp}` (more than 1 link → `pending`, else `approved`; email/IP never returned). Like and comment routes have their own per-IP limiters keyed on X-Forwarded-For. Admin moderation: `/blog-comments` (auth + `Blogs`: GET list with `counts`, PATCH `{status}` approved|pending|hidden, DELETE). `GET /blogs/dashboard-stats` also returns `likeCount`/`commentCount` on `topPosts` (ordered by views + likes) and `engagement { views, likes, comments{approved,pending,hidden}, series[30 days {date, likes, comments}] }`. Only live posts: `liveWhere()` = published (or scheduled whose date passed), publishDate empty/past, expiryDate empty/future; also used for `blogs` in `GET /sitemap`. The admin blog routes (`/blogs` CRUD) still have no auth.
- Forms (`FormService.js`): admin CRUD, `GET /forms/public/:idOrSlug`, and `POST /forms/public/:idOrSlug/submit`.
  - Validates the submission against the field definitions, has an `_hp` honeypot, and saves it as an `Inquiry` (CRM lead, `formData` JSON) via `mapTo` fields (`name` and `email` required).
  - Emails a notification unless `settings.sendEmailNotification === false`.
  - Field types: text, email, phone, number, textarea, select, radio, checkbox, date, hidden.
- Packages: `packageController` / `PackageService`. A package has `pricingPlans[]` (duration, monthlyPrice, originalTotal, savePercentage, keywords, link), optional `keywordTiers[]`, and `features { sections[], collapsedCount }`.
- pSEO AI generation (`AiGenerationService`): provider (OpenAI / Anthropic / Gemini), model, system prompt, sections, word tiers and tones all come from the `ai_settings` table (scope `pseo`, `AiSettingsService`). The admin edits them at `/seo-pages/ai-settings`.
  - API keys are AES-256-GCM encrypted (`utils/secretBox.js`, key from `AI_SETTINGS_SECRET`, falling back to `JWT_SECRET`). If that secret changes, the keys must be re-entered. Keys never leave the API unmasked.
  - Provider calls are plain REST over `fetch` (`services/ai/providers.js`, no SDKs). If no provider is active, generation falls back to `.env` `GEMINI_API_KEY` + `gemini-3.5-flash`.
  - Only the JSON output contract in `_buildContextualPrompt` stays in code, because the parser depends on it. Its rule 2 asks for Tailwind CSS utility classes only (no Bootstrap classes, inline styles or style/script tags; icons as `<i class="bi bi-…">`).
  - `/seo-pages/ai-*`, `generate-ai` and `bulk-generate-ai` require auth + the `SEO` permission. The other `/seo-pages` routes are still open.
- Menus (`/menus`, `location: header|footer`), about page (`/about-page`, a singleton), service categories, SEO pages (pSEO: states, locations, industries, technologies, problems), media library, blogs, inquiries (CRM), audit and system logs.
- pSEO master data (India): `node scripts/seed-pseo-india.js [--dry-run]` seeds all 36 states / UTs, ~550 cities and Delhi business areas (Locations, with a local-business description the AI uses), 76 tax-related industries, ~57 technologies (accounting / ERP / payroll software, government portals, marketplaces; `category`) and 77 tax and compliance problems (`problemType`). Data lives in `scripts/data/pseo-india-locations.js` (cities; `[name, slug]` for names found in two states, `HUBS` for the profile of major hubs) and `scripts/data/pseo-india-catalog.js`. Re-runnable: matched by slug, never deletes or overwrites, only fills empty description / category / problemType / stateId. Add new entries to those files and run it again.
- Admin SEO pages list: `GET /seo-pages/admin-list` (auth + SEO read; page, limit, search, status, pageType, ai, serviceId, live=1, sortBy/sortOrder whitelisted; no longDescription but hasContent / contentLength and dimension names; `counts` for the cards) and `POST /seo-pages/bulk-status { ids, status?, indexable? }` (auth + SEO update; skips publishing pages without content). `POST /seo-pages/bulk-generate-ai` also takes `ids` (exactly those pages, max 20) instead of the next drafts.
- `GET /seo-pages/combos`: every pSEO page as id, slug, serviceId, locationId, industryId, technologyId, problemId, status (no content), for the admin Matrix Combinator duplicate check. Location lists (`LocationRepository.findAndCountAll`) include `stateMaster` { id, name, slug }.
- SEO pages: `GET /seo-pages/lookup?path=` (one page with its service sections hydrated and location → state/country), `/seo-pages/by-service/:idOrSlug` (location/industry/... clusters, locations A-Z) and `/seo-pages/related` only return `status: 'PUBLISHED'` pages with content and an active location; DRAFT/ARCHIVED stay hidden. The first update to PUBLISHED stamps `publishedAt`.
- SEO Configs (`/seo`, table `seos`, migration `20261017000001-add-target-and-details-to-seos.js`): one override per website page, `targetType` service | page | seo_page | static (home/about) | custom + `targetId`; `SeoController` derives `route`/`targetLabel` from the picked record, keeps one config per page/URL and validates the JSON-LD. Only `GET /seo/lookup` is public (by type+id, else route; rows without targetType are ignored); the rest needs auth + the `SEO` permission.
- `GET /sitemap` (public, `SitemapController`): published services/pages, published pSEO pages with content (+ `indexable`), the about page date and active SEO Configs' robots/canonical — ids, slugs and dates only. The website's /sitemap.xml applies the listing rules.
- Dashboard (`GET /dashboard/stats`, auth, `DashboardController`): `counts` (every module by status; services exclude the `old-service-data` category, counted as `services.old`), `leads` (today / 7 days / month vs last month, by status / source / form, 30-day `series`, 6 latest), `attention` (new + high-priority leads, drafts, live services without meta title/description, Trash count as listed on the Trash page), `media` (files, size, active storage), `recentActivity` (audit log), `recentServices`, `topBlogs`.
- Trash (`/trash`, auth, `TrashController`): soft-deleted (paranoid) services, pages, SEO pages, SEO configs, blogs, service categories, forms and menus — `GET /trash/summary`, `GET /trash/:module`, `POST /trash/:module/restore {ids}`, `DELETE /trash/:module {ids}` (forever; only already-trashed rows; also removes a service's sections / a menu's items). Each action needs the module's permission (`MODULES`); the audit hooks log DELETE / RESTORE. Menus and SEO configs became paranoid in migration `20261017000002-soft-delete-menus-and-seos.js` (a trashed SEO config still blocks its route until restored or purged). Other modules (packages, FAQs, banners, testimonials, ...) are still deleted at once; their last data is only in the audit log (`oldData`).
- Media storage (admin: Media → Media Settings; `services/storage/`): `storage_settings` (one row, migration `20261017000003-media-storage-settings.js`) holds `activeProvider` (`local` = the backend's uploads/ folder, the default) and every saved provider's settings, secrets encrypted with `utils/secretBox.js`. `providers.js` lists the providers (local, s3, r2, spaces, wasabi, b2, gcs, custom), all S3 API through `@aws-sdk/client-s3`. `StorageService.upload` stores with the active provider and returns `{ url, storageType, storageKey }` (saved on the media row); `remove(media)` deletes from the provider the file was stored with; `testConnection` uploads a test file, fetches it from the public URL and deletes it; `save` activates a cloud provider only after that test passes. Form uploads that use multer disk storage (banners, about, countries, partners, team) go through `StorageService.storeDiskUpload`. The old `.env` `USE_S3_STORAGE` / `AWS_*` switch is gone. Media delete is a soft delete (Trash → Media); only "Delete forever" removes the stored file. A folder delete (`MediaFolderService.delete`, migration `20261017000004-soft-delete-media-folders.js`) also goes to the Trash (`media-folders`): its subfolders and files are soft-deleted with `trashedWithFolderId` = that folder, hidden from the Trash lists (`MODULES.hidden`) and restored / purged with it; a file or folder restored while its parent folder is still trashed moves to the top level. All `/media` routes need auth + the `Media` permission. Uploads (`MediaService.processAndUpload`) convert images to WebP with sharp; an image sharp cannot read (.ico, .bmp, .heic, broken file) is stored as uploaded. `POST /media/upload/bulk` handles each file on its own: 201 with `data` = saved files and `errors` = [{ field: file name, message }] for the failed ones, 422 only when none was saved.

## Known issues
- `app.js` has no `app.set('trust proxy', ...)`. Both the global `/api/` limiter (100 req / 15 min in production) and the form submit limiter (20 / 15 min) key on `req.ip`. Behind the Next.js server or any proxy, every website visitor shares one bucket. Fix this before production.
- CORS is `origin: '*'`.
- `GET /services/slug/:slug` also returns draft services. The website renders anything that is not deleted.

## Site settings
- `GET/PUT /settings/:group` (`SettingController`, key/value rows in `settings`; objects are stored as `json`). The website reads `organization` (logos, favicon), `contact`, `address` and `social`.
- `menus.settings` (TEXT holding JSON, parsed by the model getter; migration `20261016000000-add-settings-to-menus.js`): display options of a menu. The footer menu (location `footer`) stores the website footer options there. Menu items nest through `parentId`; the repository returns three levels, which the footer uses (main heading → column → link). Migration `20261016000001-seed-footer-menu-sections.js` added the uirefrence.html footer sections to the footer menu.
- `menu_items.icon` (migration `20261017000000-add-icon-to-menu-items.js`): emoji or image URL, saved by `MenuService.updateMenuWithItems`; the website header shows it beside dropdown links.
- `scripts/seed-reference-header.js` (`--dry-run` first) seeds from `scripts/data/reference-header.json` (extracted from the website's uirefrence.html): service categories, one service per reference header service link with reference-style Page Builder blocks (PUBLISHED when the reference has written content, else DRAFT), and the header menu "Main Header" (made active; other header menus set inactive, not deleted). Re-runnable: existing slugs (services or pages) are skipped, the menu items are rebuilt.
- Neither route has auth: anyone can read every group (including SMTP / payment secrets) and PUT any group. Needs fixing before production.
- Roles / permissions catalogue: migration `20261023000002-seed-admin-all-and-crm-manager.js` holds every (module, action) the code checks (`CATALOGUE`), links all of them to the Admin role and creates the **CRM Manager** role (CRM + Inquiries full, Forms read, Dashboard read). A new module's permissions need a seed migration like it (and the Admin link).
- `GET /roles/:id` includes the role's permissions (`RoleService.getById` → `findByIdWithPermissions`). Saving the admin Role form replaces the role's permissions with the ticked ones, so without them a save emptied the role.
- Custom robots.txt (`controllers/RobotsTxtController.js`, routes in `seoRoutes.js`): `GET /seo/robots-txt/public` (website, `{ content: null }` = automatic), `GET` / `PUT /seo/robots-txt` (SEO read / update; body `{ content, enabled }`, max 64 KB, control characters stripped). Stored in `settings` group `seo`: `robots_txt`, `robots_txt_enabled`.
- SEO Configs `targetType: 'landing'` (targetId = landing page id): `resolveTarget` stores the full landing URL (`landingUrl(slug)`) as `route` (unique, never a main-site path). The public landing payload (`LandingPageService.toPublic`) includes `id` so the website can look the config up.
- Form fields "Options from": `services/forms/optionSources.js` (SOURCES: services [filter categoryId], service_categories, landing_pages, pages, countries, states, locations, industries; only published / active rows, value = name; 60 s cache cleared by save / delete hooks on those models, so publish / draft shows at once). `FormService.toPublicLive` (public form + `_loadForms` hydration) and `submit` use `withLiveOptions` (site list + typed extras). `_normalizeFields` keeps `optionsSource` / `optionsFilter`; such a field needs no typed option. Admin: `GET /forms/option-sources` (sources + counts) and `/forms/option-sources/:key` (read Forms).
- Landing custom themes: `services/landing/customThemes.js` ("My themes", settings group `landing` key `custom_themes`, max 40, hex colours brand / accent / deep), `GET /landing-pages/themes` (read) and `PUT /landing-pages/themes` `{ themes }` (update), before `/:id`. `landingValidation` rejects a Header `customTheme` whose colours are not `#rrggbb` (they become CSS); test in `tests/landing.test.js`.
- Landing page addresses moved (2026-10-26) from subdomains to `<main site>/lp/<slug>`: `services/landing/subdomain.js` `landingUrl` / `landingPath` (.env `LANDING_SITE_URL`, else `SITE_URL`, default https://taxalphonic.com); the slug keeps the old label rules; editor messages say "URL name". SEO Config route of a landing page = `/lp/<slug>` (older rows keep the full subdomain URL until saved; the website looks configs up by id).
- Correction (2026-10-26): landing pages are at `https://services.taxalphonic.com/lp/<slug>` (`landingUrl`, .env `LANDING_SITE_URL`, default that origin; SITE_URL is no longer used for it). "services" is a reserved slug.
- Sequelize SQL logging is off (`config/config.js` `logging: false`); set `DB_LOG_SQL=true` in .env to print every query while debugging.
- Slugs never clash (`services/slugRegistry.js`): services, CMS pages and pSEO pages share the website URL space (`taxalphonic.com/<slug>`); blogs, service / page / blog / portfolio categories, blog tags, portfolio items and forms are each their own namespace. Trashed rows keep their slug. Paths the website serves itself (`about`, `blog`, `explore`, `lp`, `category`, `sitemap.xml`, … `RESERVED_SITE`, keep in sync with the website's `app/`) cannot be service / page / pSEO slugs (the page `home` and `landing-page/<name>` drafts excepted). `watchSlugs()` (called in `app.js`) adds model hooks: create, a changed slug and a restore from Trash throw 409 with the record that holds the slug; unchanged old slugs are never re-checked. pSEO bulk-generate skips such slugs into `overlaps`. Admin live check: `GET /slugs/check?type=&slug=&id=` → `{ available, reason, conflict { label, name, adminUrl, trashed }, suggestion }`. Tests: `tests/slugRegistry.test.js`. Landing pages keep their own check (`/landing-pages/check-slug`).
- Bundle packages: a package can include several services (`features.includedServices` = `[{ serviceId | null, title, label, note }]`, inside the features JSON, no migration). `PackageService.withIncludedServices()` resolves them for Packages blocks and `GET /packages/:id` into `includedServices: [{ title, note, url }]`: a published service gives its current title (or `label`) and `/<slug>`; a draft / deleted service or a custom item keeps its saved title, no link.
- `GET /auth/me` (routes/authRoutes.js, any logged-in user): the user with the role's current permissions; the admin reloads it on start. `GET /dashboard/stats` returns only the figures of modules the user may read (`forUser` in DashboardController: other counts zero, lead details / activity / recent lists empty, same shape).
